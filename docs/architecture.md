# 架构与产品决策

## 产品判断

“正文 + 可跳转故事地图”是可行且有辨识度的方向。它解决的不是排版，而是长篇写作时在“想剧情”和“写正文”之间频繁切换的问题。

产品中最重要的约束是：章节和节点是不同对象，链接只是它们之间的关系。节点的位置、形状、便签内容不应写进正文；正文也不应嵌入画布数据。

## 当前 MVP

```text
手机 / Windows 浏览器（PWA）
        │ HTTPS + JSON API
        ▼
FastAPI 自托管服务
        │
        ▼
SQLite 持久化文件
```

前端为静态 PWA，用户在设置中填写后端地址。后端不依赖前端域名，可以单独部署和升级。当前数据关系如下：

```text
Project
 ├─ Volume[]
 │   └─ Chapter[]
 └─ StoryMap[]
     ├─ Node[] ── optional chapter_id ──> Chapter
     │   └─ NodeNote[]
     └─ Edge[] ── source_id / target_id ──> Node
```

## 已确认的设计优点

- 节点和箭头都可链接并跳转章节，章节正文也能返回对应地图元素，形成双向导航。
- 同一作品可以维护多张独立故事地图；切换地图不会混用节点、连线、便签、视野状态或章节链接。
- 节点便签与章节正文分离，适合保存写作意图、伏笔和待办。
- 同一画布可以混合情节、人物、地点和冲突，而不是只做树状脑图。
- 前后端分离后，社区可以独立开发 Web、桌面或移动客户端。
- PWA 先覆盖手机和 Windows，避免一开始维护三套客户端。

## 需要注意的边界

### 同步不是“把请求发到服务器”这么简单

当前 MVP 是最后一次保存覆盖前一次保存，适合单设备或避免同时编辑的使用方式。正式多设备版本需要：

- 每条记录增加 `revision` 或 ETag；
- 客户端提交基于哪个版本；
- 版本冲突时保留两份内容并让用户合并；
- 本地离线队列与断线重传；
- 服务器快照和恢复入口。

在这些能力完成前，不应宣传“无冲突离线同步”。

### 公网服务必须有身份系统

当前可选 API Key 是单人自托管的最低保护，不适合开放注册。公开实例至少需要用户表、密码哈希或 OAuth、项目所有权校验、请求限流和审计日志。

### SQLite 适合个人，不是多人协作终点

SQLite 很适合零运维自托管。多人同时写作、评论或共享项目时应支持 PostgreSQL。数据库层应保持清晰，避免把 SQLite 特有语法散落到业务代码。

### “节点链接写作资源”的未来扩展

当前每个节点和箭头最多链接一个章节。如果未来要让它们同时链接多个章节、人物卡和资料，应把 `chapter_id` 升级为独立的 `resource_links` 表，而不是不断增加外键字段。

### 旧版场景迁移

后端升级到 0.8.0 后，会在启动时把旧版二级场景按原章节顺序提升为独立章节，并把原先指向场景的节点改为指向新章节。兼容表和字段暂时保留在 SQLite 中，仅用于安全迁移旧数据，不再通过 API 或前端暴露。

### 旧版单画布迁移

后端升级到 0.9.0 后，会为每个旧作品自动创建一张“主故事线”，并把原有节点、箭头和便签归入该地图。新建地图后，节点与箭头都必须归属同一张地图，后端会拒绝跨地图连线；删除或清空地图只影响该地图，不会删除章节正文或其他地图的数据。

### 故事卷迁移

后端升级到 0.10.0 后，会为每个旧作品创建默认“第一卷”，并把原有章节归入其中。删除含章节的卷时，章节会移动到另一卷，正文与节点、箭头的章节关联均保留；每个作品至少保留一个故事卷。

### TXT 章节导入
API 0.11.0 支持将多个 TXT 文本原子性地批量导入到指定故事卷，每个文件创建为一个新章节，标题按目标卷的现有顺序自动编号。前端从作品目录旁的统一“导入/导出”入口进入，支持 UTF-8、GB18030/GBK 和 UTF-16 LE。单 TXT 导入也可以改为覆盖一个已选章节的正文，此模式保留已有章节标题和故事地图关联。为兼容旧版章节导出，导入时若文件首行与文件名一致，会将重复标题行剥除。导入纯文本时将单个换行编码为 Markdown 硬换行、空行编码为段落分隔，稿纸模式下段间距按完整行高设置，避免和横线错位。

全书 TXT 导入在前端按 `【卷】` / `【章节】` 标记、Markdown 标题或“第 N 章”等常见标题拆分文本，再通过章节批量导入 API 追加到指定卷；没有识别到章节标题时将整份文本作为一章导入。

TXT 导出在前端完成，可从章节列表单选或多选章节，也可导出全书。单选下载独立章节文件；多选可合并为一个 TXT（按故事卷和章节顺序组织并保留卷名、章节标题），或逐章分别下载；全书导出保留全部卷与章节。组合导出使用 `【卷】` / `【章节】` 标记，以便再次导入时准确拆分。下载文件采用 UTF-8 BOM 与 CRLF 换行，便于 Windows 文本编辑器识别。完整项目包、故事地图与 Markdown 导入导出仍属于后续规划。

## 建议路线

1. 先用当前 MVP 验证写作流程和画布交互。
2. 增加 ZIP/Markdown 导入导出、每日快照和备份恢复。
3. 实现 revision 冲突检测与离线队列。
4. 增加账户和项目权限，再支持公网多用户。
5. 用 Tauri 打包 Windows 客户端，共用现有前端。
6. 最后再考虑实时协作；它会显著增加数据模型和运维成本。

## 部署原则

- 前端和后端都使用 HTTPS；HTTPS 页面不能调用 HTTP API。
- 将 `LEE_CORS_ORIGINS` 限制为实际前端域名，不要在公网长期使用 `*`。
- 设置足够长的 `LEE_API_KEY`，并定期备份 SQLite 文件。
- 反向代理限制请求体大小并配置访问日志。
- 更新服务前先生成数据库快照。
